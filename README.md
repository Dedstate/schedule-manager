# «Ничего не падает» — работа с расписанием

Вы разрабатываете консольное приложение на Kotlin. Главная задача — модель занятий, которую нельзя испортить через
публичный API, делегирование реестра и ошибки разбора как данные.

**Одна итоговая сдача, два логических этапа:** сначала модель и реестр, затем разбор строк и обработка команд. Срок
указан в Academy.

- [Условие задания](docs/assignment.md): требования, формат файла и вывода.
- [Памятка](docs/student-guide.md): готовый запуск, чтение строк, защита коллекций и тесты.

## Что уже готово и что нужно написать

| Файл                                        | Назначение                                                           |
|---------------------------------------------|----------------------------------------------------------------------|
| `app/src/main/kotlin/schedule/Cli.kt`       | Готовый разбор аргументов и проверка параметров                      |
| `app/src/main/kotlin/schedule/Main.kt`      | Готовый выбор обработчика, сообщения об ошибках аргументов и чтения  |
| `app/src/main/kotlin/schedule/FileLines.kt` | Готовое чтение файла по строкам с номером строки                     |
| `app/src/main/kotlin/schedule/Commands.kt`  | Заглушки `runPeriod`, `runType` и `runErrors`, которые вы реализуете |
| `app/src/test/kotlin/schedule/CliTest.kt`   | Тесты готового запуска и чтения                                      |

Создайте свои классы занятий, реестр, обёртку с журналом, парсер строк, типы отказов, форматтер и тесты. Готовый
`SessionType` описывает метки команд; он не заменяет доменную модель. Переписывать разбор аргументов не требуется.

В исходном шаблоне корректные команды печатают `Not implemented: period`, `Not implemented: type` или
`Not implemented: errors` и завершаются с кодом `2`. Замените эти заглушки своей реализацией. После завершения работы
такие сообщения выводиться не должны.

## Начало работы

1. Сделайте Fork и клонируйте свою копию репозитория.
2. Установите **JDK 25**. Укажите его в `JAVA_HOME` и выберите JDK 25 для Gradle в IntelliJ IDEA.
3. Для генератора и проверки примеров нужен **Python 3.10+**.
4. Прочитайте условие и посмотрите `samples/`.
5. Размещайте свой код в `app/src/main/kotlin`, тесты — в `app/src/test/kotlin`.

В проекте используются Kotlin **2.4.10**, Gradle **9.5.1** и JUnit **6.1.3**. Kotlin и Gradle отдельно устанавливать не
нужно: используйте Gradle Wrapper. Первая сборка загружает зависимости из интернета.

Команды, типы в файлах, сообщения и примеры вывода — на английском. Учебные темы, места и имена записаны латиницей.
Отсутствующее значение обозначается `-`.

## Сборка и запуск

Откройте Terminal в IntelliJ IDEA или отдельный терминал **в корне проекта**, где находятся `gradlew.bat`,
`settings.gradle.kts` и `samples/`. На Windows вместо `python` можно использовать `py -3`; на Linux/macOS — `python3`.

Windows PowerShell:

```powershell
.\gradlew.bat build :app:installDist
.\app\build\install\schedule\bin\schedule.bat period --file samples/clean.txt --from 2026-09-28 --to 2027-05-13
.\app\build\install\schedule\bin\schedule.bat type --file samples/dirty.txt --type EXAM
.\app\build\install\schedule\bin\schedule.bat errors --file samples/dirty.txt
```

Linux/macOS:

```bash
bash ./gradlew build :app:installDist
./app/build/install/schedule/bin/schedule period --file samples/clean.txt --from 2026-09-28 --to 2027-05-13
./app/build/install/schedule/bin/schedule type --file samples/dirty.txt --type EXAM
./app/build/install/schedule/bin/schedule errors --file samples/dirty.txt
```

`build` компилирует приложение и выполняет тесты. `installDist` создаёт скрипты запуска. Условное имя `schedule` в
задании обозначает это приложение: терминал сам по себе такой команды не знает.

Во время разработки можно запускать через Gradle:

```powershell
.\gradlew.bat :app:run --args="period --file samples/clean.txt --from 2026-09-28 --to 2027-05-13"
```

Аргументы получает готовая `main(args)`; она вызывает вашу функцию обработки. Относительный путь к файлу отсчитывается
от рабочей папки. Путь с пробелами заключайте в кавычки при запуске скрипта приложения.

Для проверки кодов завершения используйте скрипт приложения или `tools/verify.py`: при коде `1` или `2` команда Gradle
`run` дополнительно сообщает о неуспешном завершении процесса.

## Проверка решения

После реализации и сборки:

```text
python tools/verify.py
```

Проверяются небольшие файлы, вывод всех четырёх типов, октябрьский диапазон, ошибки аргументов и чтения. Сравниваются
текст и коды завершения; LF и CRLF в выводе считаются эквивалентными. Отчёт сохраняется в
`verification/acceptance.json`.

| Входной файл        | Содержание            |
|---------------------|-----------------------|
| `samples/clean.txt` | 200 корректных строк  |
| `samples/dirty.txt` | 500 строк, 164 отказа |
| `samples/empty.txt` | Ни одной строки       |

В `samples/*.expected` находятся эталоны. `clean.expected` — полный диапазон для `period`. Эталоны `*.type.expected`
относятся к `--type EXAM`. `dirty.october.expected` — `period` с `--from 2026-10-01 --to 2026-10-31`; код завершения
`1`, поскольку проверяется весь файл.

Добавьте собственные тесты на инварианты модели, защиту списков, делегирование, приоритет ошибок и границы фильтров:
совпадение с эталонами не заменяет эти проверки.

### Дополнительный большой файл

`huge.txt` содержит два миллиона строк. Это дополнительная проверка после знакомства с коллекциями и
последовательностями:

```text
python tools/generate_samples.py --huge
python tools/verify.py --huge
```

Большой файл исключён из Git. Обычная проверка его не требует. Повторно создать небольшие примеры можно командой
`python tools/generate_samples.py`; не меняйте эталоны под своё решение.

### GitHub Actions

На push и pull request запускаются сборка, тесты и проверка согласованности примеров на Windows и Linux. Базовая
проверка проходит уже в шаблоне: она проверяет готовый код и написанные вами тесты, **но не подтверждает выполнение всей
лабораторной**.

Для полного сравнения вывода откройте Actions → schedule-lab → Run workflow и включите `acceptance`. Для большого файла
дополнительно включите `huge`. Полная проверка должна пройти на готовом решении; исходные заглушки её не проходят.

**Автоматические проверки предназначены для самопроверки.** В репозитории уже есть тесты готового запуска и сравнение
вывода с эталонами на заданных примерах. Их успешное прохождение помогает понять, что основные проверяемые сценарии,
скорее всего, реализованы верно. Но это ограниченный набор тестов: он не доказывает правильность решения во всех случаях
и не означает автоматическую сдачу работы.

**Основную проверку и итоговую оценку проводит лабник.** Он изучает код, проверяет устройство модели, соблюдение
инвариантов, защиту коллекций, делегирование, обработку ошибок и пограничные случаи. Собственные тесты и объяснение
принятых решений остаются обязательной частью работы.

## Как устроено моё решение

Разбор аргументов и точку входа оставил как в шаблоне. Основная логика находится в `Session.kt`,
`Repository.kt`, `Parser.kt`, `Formatter.kt` и `Commands.kt`. Модель отвечает за
корректность занятия, парсер за ошибки во входной строке, а обработчики команд за выборку и вывод.

### Модель занятий

В основе `sealed interface Session` с датой и темой. Для лекции, практики и сдачи есть общий `ActiveSession` с местом
и преподавателями. `Cancelled` реализует только `Session`, полей `location` и `teachers` у него вообще нет, что
обеспечивает null-safety.
Для четырёх типов я выбрал обычные `class`, а не `data class`. В конструктор передаётся список преподавателей, но
хранить исходную ссылку нельзя. Обычный класс позволяет сразу сохранить защищённую копию списка и не выставлять входной
параметр наружу как свойство. При этом сравнение по значению, `hashCode` и `copy` всё равно реализованы. `copy` создаёт
новый объект через тот же конструктор => обхода проверок через него нет.

Валидация сделана на уровне самих классов. Например, прямой вызов `Exam(...)` с одним
преподавателем завершится `IllegalArgumentException`. Значения автоматически не исправляются. `trim()`,
приведения к одному регистру или удаления повторов нет.

### Почему нельзя изменить список преподавателей

При создании занятия список копируется в новый `ArrayList`, а наружу выдаётся `Collections.unmodifiableList`. Здесь
важно все. Без копирования можно было бы поменять уже созданное занятие через старую ссылку, а без неизменяемой
обёртки через свойство `teachers`.

В `InMemorySessionRepository` похожая логика. `all()` возвращает отдельный неизменяемый снимок. После следующего `add`
ранее выданный список не изменяется. Реестр хранит занятия в списке, а не в `Set`, потому что одинаковые записи по
условию допустимы и их порядок важен.

### Реестр с журналом

Для `AuditedSessionRepository` использовано именно `SessionRepository by delegate`. Операция `all()` делегируется без
дополнительной логики, а `add` и `addAll` переопределены, чтобы после успешного добавления записать событие и обновить
счётчик.

Переопределить только `add` недостаточно, т.к реализация `addAll`, полученная через `by delegate`, вызывает внутренний
метод, а не `add` у обёртки. Поэтому `addAll` нужно учитывать отдельно. За один вызов записывается одно
событие, даже если добавлено несколько занятий. Пустой список тоже даёт событие с количеством `0`. Если делегат выбросил
исключение, журнал и счётчик не обновляются.

### Разбор входного файла

`parseScheduleLine` возвращает `ParseResult.Success` с готовым занятием либо `ParseResult.Failure` с номером строки и
конкретной `RejectionReason`. Это удобнее, чем исключение для каждой испорченной строки, т.к обработчик может продолжить
чтение и в конце правильно посчитать отказы.

Отдельно я следил за приоритетом ошибок. Например, в строке с неверной датой и неизвестным типом сначала должна
обнаружиться дата. У сдачи с одним допустимым именем и вторым `-` проверка количества преподавателей идёт раньше
проверки самого имени. За текст ошибки отвечает `Formatter.kt`.

Возможные ситуации при парсинге:

| Ситуация                   | Текст                                                    |
|----------------------------|----------------------------------------------------------|
| Управляющие символы        | `control characters in field "FIELD": "VALUE"`           |
| Пробелы в начале или конце | `outer whitespace in field "FIELD": "VALUE"`             |
| Лишние данные у отмены     | `field "FIELD" must be "-" for "CANCELLED", got "VALUE"` |
| Недопустимое место         | `invalid location "VALUE"`                               |
| Недопустимое имя           | `invalid teacher name "VALUE"`                           |
| Повтор преподавателя       | `duplicate teacher "VALUE"`                              |

Команды `period` и `type` проверяют весь файл, даже если большинство занятий не подходят под фильтр, иначе можно было бы
потерять ошибки вне выбранного диапазона и вернуть неверный код завершения. Чтение идёт построчно через готовую
`forEachScheduleLine` без загрузки файла целиком в память.

### Проверка инвариантов

Вот проверки самой модели напрямую:

1. **Пустая или пробельная тема** не проходит проверку в конструкторе.
2. **Год `0` или `10000`** отсекается проверкой допустимого диапазона года.
3. **Лекция или практика без преподавателей** не проходит проверку минимального размера списка.
4. **Сдача с одним преподавателем** невозожна, т.к конструктор требует как минимум двух.
5. **Сдача с повторяющимися именами** — повтор выявляется через `HashSet`; регистр при сравнении учитывается.
6. **Изменение списка, переданного в конструктор** не влияет на объект, потому что у него своя копия.
7. **Попытка изменить `teachers` через публичное свойство** отклоняется неизменяемой обёрткой.
8. **Некорректные аргументы `copy()`** снова проверяются конструктором нового объекта.
